# 里程碑 bring-up 计划流程（openvela × P4X 实证版）

## 使用时机

- 开新里程碑 / 大功能，或既有问题需要定修复路线
- 需要向 openvela 上游提交补丁 / 驱动
- 修复方向出现多个候选，需要用户拍板

## Step 1：开工三读

1. 本仓 `README.md`——作品概述、验证状态（§6）与已知约束（§7）的权威。
2. `docs/PROJECT_PLAN.md`——功能清单、里程碑回顾、剩余工作。
3. `board/esp32p4_function_ev/`——板级事实（`pins.md`）与阶段化配置（`defconfig.inc`）。

## Step 2：调研先行（严禁无出处推断）

| 顺序 | 动作 | 产出 |
|------|------|------|
| 1 | 驱动 / 组件 Kconfig + 源码（记 `文件:行号`），并与实物核对 | 行为约束清单 |
| 2 | 官方文档 / 上游例程同场景用法 | 可抄的正解形态 |
| 3 | 该组件已知 issue / PR（含 open-vela 与上游社区） | 避坑记录 |
| 4 | 结论登记出处（官方文档 / 源码行号 / issue / 实测，四选一） | 无出处的结论只能作「待验证假设」 |

**PR 考古方法**：本队移植期的 16 条踩坑全部经 PR 描述（nuttx #347 / #364）、commit 记录与会话日志恢复（现象 / 根因 / 处置 / 出处四元组齐全）——踩坑记录随手归档到可溯源载体，是「我都忘了踩了多少坑」的解药。

## Step 3：方案候选 → 用户拍板

凡架构改动、组件选型、修复路线分叉，先给候选清单，**用户拍板后才动手**（实现层细节可自主）：

```markdown
| 方案 | 怎么做 | 代价 | 风险 | 适用前提 |
|------|--------|------|------|----------|
| A（推荐） | ... | ... | ... | ... |
| B | ... | ... | ... | ... |
```

推荐项必须给理由；否决项必须写否决依据（进会话日志 / 计划文档）。

## Step 4：计划落盘

- 落盘位置：`docs/`（先例：`PROJECT_PLAN.md` 功能清单 + 里程碑回顾）。
- 阶段划分参照 `defconfig.inc` 的实证顺序：**阶段 1 显示 → 1b 音频 → 2 摄像头 → 3 推理 → 4 应用**——一次只放开一层依赖，多个未知问题的症状叠加会使排查成本组合式增长。
- 计划内每一步必须**可独立验收**，附预期现象。

## Step 5：实施纪律

- **单步串行**：一次只做一个可验收步骤，完成即停，等确认再继续。
- 服务重构必须带**行为对照清单**（重构丢功能、隔轮才发现是真实发生过的事故模式）。
- 模块单一职责：应用按 `signbridge_*.c` 每文件一职责的先例组织，可调参数集中一处，严禁回填入口文件。
- 板不在位（串口探测不到目标板）时**止步构建交付**，不烧录、不视为验收。

## Step 6：验收门（验证红线）

- **严禁**以「编译通过 / 串口无报错」宣布问题解决。
- 每次交付附实体机测试方案：

```markdown
| 步骤 | 操作 | 预期现象 |
|------|------|----------|
| 1 | ... | ... |
```

- 负面检查项必列：花屏 / 撕裂 / 闪烁 / 触摸落点 / 帧率（对照各专项技能的基线与注意事项）。
- 结论以用户实体机确认为准——**用户说没问题才是没问题**。
- 未完成的链路在文档与技能中如实标注「待复验」，不得写成已验收。

## Step 7：上游 PR 协作纪律（openvela 特有成本，先备后提）

| 项 | 纪律 | 实证 |
|----|------|------|
| CLA | 首次提交前在官网签署，未签 CI 必挂 | #347/#364 均经历签署后重跑 |
| 注释语言 | 源码注释**全量英文**——中文注释被上游 CI 整体拒绝 | #364 全量翻译返工 |
| 代码规范 | nxstyle（头注释格式 / 头文件保护宏 / 换行规则）+ cmake-format 提前本地自查 | 规范违规多轮打回（#347/#364） |
| 补丁目标 | 「进上游」而非「绕过去」——上游流程换来强制性代码审校 | 自研 gt9xx / CSI 驱动的提交路径 |
| 文档失真 | 注释 / Kconfig 描述与实物不符也是缺陷，一并修正 | #347（接线描述、分辨率注释） |

## Step 8：收工

- 产生文件变更 / 决策 / 踩坑 → 按大赛《AI Coding 日志归集与提交手册》导出会话日志到 `logs/`（目录结构见 `logs/README.md`）。
- 烧录 / 抓日志 / 串口判读的操作细节走 `board-flash-monitor` 技能；各外设症状对照走对应专项技能，本流程不重复。
